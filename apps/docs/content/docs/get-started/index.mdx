---
title: Get started
description: Install one SDK package and decorate your agent without changing its reply call sites.
---

Just look at this:

```bash
npm install @trustloopguard/sdk
```

```ts
import { guardAgent } from '@trustloopguard/sdk';

const agent = guardAgent(createAgent(), { agentId: 'support-agent' });

const reply = await agent.reply(userMessage);
sendToUser(reply);
```

That is the primary TrustLoopGuard integration. Install one SDK package,
decorate the agent once where it is created, and keep the rest of your
application calling `agent.reply(...)`. No repository clone, local
TrustLoopGuard server, proxy configuration, or manual decision branching is
required.

## 1. Create an Agent and Runtime Key

In the TrustLoopGuard dashboard, create an agent and runtime API key. Copy the
agent ID, API URL, and key.

## 2. Install One Package

```bash
npm install @trustloopguard/sdk
```

## 3. Configure

Set the URL and runtime key shown in your workspace:

```bash
export TLG_URL=https://api.gettrustloop.app
export TLG_API_KEY=tl_live_...
```

## 4. Decorate Your Agent Once

```ts
import { guardAgent } from '@trustloopguard/sdk';

const agent = guardAgent(createAgent(), { agentId: 'support-agent' });

const reply = await agent.reply(userMessage);
sendToUser(reply);
```

The original agent should expose
`reply(message: string, ...args): Promise<string>`. `guardAgent(...)` returns
the same agent type, so existing `agent.reply(...)` call sites remain
unchanged.

If your app currently has a helper like this:

```ts
async function generateReply(message: string): Promise<string> {
  return await agent.reply(message);
}

const reply = await generateReply(userMessage);
sendToUser(reply);
```

decorate the agent before that helper uses it:

```ts
const agent = guardAgent(createAgent(), { agentId: 'support-agent' });
```

Do not add guard checks to every helper or handler. The decorated agent keeps
the same `reply(...)` surface.

For every call, the original agent produces a draft, the decorator submits that
draft directly to the Rust API at `POST /v1/events`, and the returned decision
is applied before `reply()` resolves. The bearer key scopes the request to the
workspace and environment. The same request creates the trace shown in the
dashboard. The decorator also creates and completes one `chat_session` Run for
the reply, records the configured agent ID on that Run, and links the trace to
it. An existing explicit Run scope is reused instead of nested.

This boundary intercepts each `reply()` invocation and guards its final
response. It does not send the raw user message text in the output event by
default. Internal framework tool calls and payments require a framework adapter
or the explicit typed action helpers.

Automatic Run bookkeeping is best-effort: a Run storage failure does not
replace the guard result or the agent's own error. Set `run: false` only when
you intentionally want ungrouped traces.

## 5. Verify

Send one test message and open the agent's Run and trace in the dashboard. No repository
clone, Doppler setup, local Rust server, or model-provider proxy is required.

See [Guard Modes](/docs/guides/guard-modes) for strict, rewrite, regeneration,
and streaming behavior.
