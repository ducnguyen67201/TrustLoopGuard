# Whitepaper Coverage Matrix

This matrix tracks the gap between the TrustLoopGuard runtime-security
whitepaper and the product code. It is intentionally conservative: a method is
`partial` until there is a Rust-owned contract, implementation, and test proving
the behavior.

Status values:

- `implemented` - shipped with tests and documented ownership.
- `partial` - core infrastructure exists, but the whitepaper method is not
  complete end to end.
- `planned` - not yet implemented; keep claims out of product docs.
- `not in scope` - explicitly rejected for this architecture.

## LLM Swap Points

All LLM use goes through `tl-llm::LlmRouter` unless a feature explicitly owns a
separate provider seam. The current route keys are:

- `hallucination`
- `tone`
- `authority`
- `semantic_policy`
- `harden_draft`
- `trajectory_diagnostic`

Operators swap providers/models in `config/llm-routing.toml` by route, using a
primary target and optional fallback. Runtime and harden code call by
`JudgeKind`, never by provider name, so adding another provider is a new
`LlmClient` implementation plus config, not a rewrite of the engine.

## Explicit Non-Goals

- Do not add a single hot-path LLM that finalizes every allow/block decision.
- Do not store durable product/security state in `apps/web`.
- Do not auto-enable harden candidates; verified survivors are still operator
  controlled.
- Do not claim all event-level hardening is complete: approval metadata,
  parameter-source metadata, and label-policy candidates are implemented, while
  missing-provenance remediation and graph-derived artifacts remain planned.
