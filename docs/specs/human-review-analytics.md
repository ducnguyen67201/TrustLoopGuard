# Human Review Analytics Spec

## Purpose

Show whether Featherlane AI reduces customer risk after an agent decision, not only whether the guardrail engine returned `allow`, `rewrite`, `block`, or `escalate`.

The existing dashboard already has an "intervention rate" chart, but that metric currently means automated guardrail interventions: `block + rewrite + escalate`. This spec adds the missing human outcome layer: what a reviewer did after Featherlane AI escalated or flagged a risky step.

## Goals

- Track human review outcomes for traces and run events.
- Show human intervention rate by run, agent, policy, workflow step, and time.
- Separate automated guardrail intervention from human intervention.
- Support non-chat workflows such as document extraction, structured output generation, background jobs, and pre-submit checks.
- Keep Rust as the durable source of truth. The web app may proxy and visualize, but must not own review state.

## Non-goals

- Featherlane AI does not become the customer's review queue or workflow orchestrator.
- Featherlane AI does not decide whether a tax return, filing, claim, or document is correct.
- The dashboard does not store review outcomes in a web-owned database.
- This spec does not add redaction or no-log behavior. See `check-redaction.md`.

## Definitions

Automated intervention:

- A Featherlane AI decision with effect `deny`, `transform`, `require_approval`, or `defer`.
- Derived from persisted traces.

Human intervention:

- A customer reviewer changed, rejected, confirmed, or otherwise acted on an agent output after a Featherlane AI decision.
- Stored as an append-only review event linked to a trace and optionally a run event.

Human review outcome:

- The latest review event for a trace when the UI needs a current status.
- The full event history remains append-only for audit.

## User Stories

- As a founder or operator, I want to know how often humans override agent output so I can tell whether the agent is improving.
- As a compliance lead, I want to see which policies cause the most human review so I can tune noisy guardrails.
- As a workflow builder, I want review metrics by workflow step so I can see whether document extraction, validation, or pre-submit review is the risky part.
- As a reviewer, I want to mark an escalation as accepted, corrected, rejected, or false positive without changing the original trace.

## Data Model

Add a Rust-owned review event model. Prefer a new durable table over mutating trace rows so the audit trail remains append-only.

Suggested table: `human_review_events`

| Field | Type | Notes |
|---|---|---|
| `id` | UUID | Generated by Rust storage. |
| `workspace_id` | text/UUID | Required for authorization. |
| `trace_id` | text/UUID | Required. Links to the decision trace. |
| `run_id` | UUID nullable | Copied from trace when available. |
| `run_event_id` | UUID nullable | Copied from trace when available. |
| `outcome` | text enum | See outcome values below. |
| `reviewer_id` | text/UUID nullable | Dashboard user or external reviewer id. |
| `reason_codes` | JSON array | Machine-readable reasons. |
| `note` | text nullable | Short reviewer note. Must be treated as possibly sensitive. |
| `created_at` | timestamptz | Server timestamp. |
| `metadata` | JSONB | Optional integration metadata. |

Outcome values:

- `accepted` - reviewer accepted the agent output.
- `corrected` - reviewer changed the output before use.
- `rejected` - reviewer discarded the output.
- `false_positive` - reviewer judged the Featherlane AI escalation unnecessary.
- `missed_issue` - reviewer found a problem Featherlane AI did not flag.
- `ignored` - escalation was not acted on.

Reason code examples:

- `bad_input_quality`
- `missing_document`
- `field_mismatch`
- `unsupported_claim`
- `policy_noise`
- `pii_risk`
- `requires_accountant_judgment`

## API Contract

Add Rust endpoints under `/v1`. Web routes may proxy these for same-origin browser calls.

```text
POST /v1/traces/{trace_id}/review-events
GET  /v1/traces/{trace_id}/review-events
GET  /v1/analytics/human-review
```

`POST /v1/traces/{trace_id}/review-events` request:

```json
{
  "outcome": "corrected",
  "reason_codes": ["field_mismatch", "requires_accountant_judgment"],
  "note": "Reviewer corrected the extracted income amount.",
  "metadata": {
    "workflow_step": "document_extraction"
  }
}
```

Response:

```json
{
  "id": "018f0c43-0000-7000-9000-000000000001",
  "trace_id": "018f0c43-0000-7000-9000-000000000000",
  "run_id": "018f0c43-0000-7000-9000-000000000002",
  "run_event_id": "018f0c43-0000-7000-9000-000000000003",
  "outcome": "corrected",
  "reason_codes": ["field_mismatch", "requires_accountant_judgment"],
  "created_at": "2026-05-19T15:00:00Z"
}
```

`GET /v1/analytics/human-review` should return aggregate rows the dashboard can render without reimplementing analytics logic client-side:

```json
{
  "summary": {
    "trace_count": 1200,
    "automated_intervention_count": 340,
    "human_review_count": 180,
    "human_intervention_count": 92,
    "human_intervention_rate": 7.67,
    "false_positive_rate": 3.2
  },
  "by_workflow_step": [
    {
      "workflow_step": "document_extraction",
      "human_review_count": 80,
      "corrected_count": 24,
      "rejected_count": 6,
      "false_positive_count": 10
    }
  ],
  "by_policy": [
    {
      "policy_id": "tax-sensitive-data",
      "escalation_count": 42,
      "corrected_count": 12,
      "false_positive_count": 4
    }
  ]
}
```

## Dashboard UX

Add or revise the analytics surface so the labels are precise:

- Keep automated intervention metrics, but label them as "Guardrail interventions".
- Add "Human intervention rate" for `corrected + rejected + missed_issue` divided by total traces.
- Add "Human review outcomes" chart with accepted, corrected, rejected, false positive, missed issue, and ignored.
- Add "Top review reasons" chart or table.
- Add breakdown by workflow step, using `run_event.kind`, `run_event.label`, or `run_event.metadata.workflow_step`.
- On run detail pages, show the latest review outcome beside each trace when available.

UI copy should avoid implying Featherlane AI owns the customer's review workflow. Use language like "review outcome recorded" instead of "assigned reviewer" unless assignment exists in the customer integration.

## Acceptance Criteria

- A trace can receive multiple review events without losing the original decision.
- The latest review outcome is visible on the run detail page.
- Analytics distinguish automated guardrail interventions from human interventions.
- Human intervention rate can be filtered or grouped by agent, policy, run kind, and workflow step.
- Web routes proxy Rust APIs and do not persist review state locally.
- Notes are treated as sensitive: no client console logging, no analytics echo unless explicitly displayed.
- Tests cover repository writes, endpoint authorization, aggregate calculations, and web transform behavior.
